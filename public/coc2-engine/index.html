§1 — Packaging

A browser game in an Electron coat

The Windows build is Electron with an almost comically thin native shell. main.js is 43 lines: open a 1920×1200 BrowserWindow, load index.html off file://, and forward five IPC messages. The preload script exposes exactly six functions.

That isSteam: () => false is the only difference between this build and the Steam one — the game asks it at startup and gates achievement reporting behind it. Notably, the app is not packed into an app.asar: resources/app/ is plain files on disk, which makes the whole thing trivially modifiable.

The same code runs in three hosts. Alongside the Electron probe there's a Cordova check (window.cordova, a deviceready listener, a user-agent mobile sniff) and a plain-browser path. Storage, fullscreen, and cloud saves each branch on which host is present.

Bundle layout

Webpack, with aggressive module concatenation — bundle 673 is 6.6 MB but only 39 top-level modules, because scope hoisting merged hundreds of source files into a handful.

Boot order

Two exported entry points do all the work: initUI() from bundle 103 and initEngine() from 81369, which immediately delegates to the real bootstrap in bundle 673. Roughly:

  1. Polyfills load, and a black splash #loading div with a <progress> element shows.
  2. initUI() constructs the UI controller, binds ~30 of its methods onto window, detects the host (Electron / Cordova / mobile), then preloads every UI sprite and vector icon by constructing Image objects and awaiting onload, ticking the progress bar per asset.
  3. initEngine() awaits all 28 content chunks sequentially, updating the splash text to "Loading Content/Khorminos…" as it goes.
  4. World construction: flags = {}, every manager is instantiated, all 467 NPCs are constructed as singletons, ~85 room-table builder functions run, and the stacks are initialised.
Worth noticing

The code-splitting is organisational, not lazy. Every content chunk is awaited during boot — the split exists so the build stays manageable and so the loading bar has something meaningful to count. On slower disks this is why the splash sits there for a while.

Identity comparison

Because instances are constructed freely from registries, identity is never ===. Everything uses is(), which accepts an instance, a constructor, or a key string, and for effects also walks an extends[] list so that, say, any variety of "Bleeding" can be matched generically.

§5 — Damage

The damage pipeline

Damage is a plain object: { attackType, damage: [{ type, amount }, …] }. A single attack can carry several typed components, and every stage of the pipeline maps over the array rather than collapsing it. CombatHelper is a static class of ~90 methods that owns the whole thing.

Hitting

Which defence is used depends on the attack class: weapon and generic evasion attacks roll against evasion(), physical against physicalRes(), magical against magicRes(), mental and tease against mentalRes(). Tease attacks are literally mental attacks — attemptTeaseHit forwards straight to attemptMentalHit.

Crits have a counter-mechanic: shieldChecks() cancels an incoming critical outright if the defender has a shield equipped, is in IceboundShield stance, or has enough stacks of ShieldingCapacitor. Three specific shields consume a charge instead.

Scaling and mitigation

Two details in that chain are worth pulling out. Variance is rolled once per attack, not per component — rand(11) produces a single multiplier in [0.95, 1.05] shared by every damage type in the array. And the difficulty multiplier is a two-column table indexed by the difficulty option:

HP and Resolve are the same pool

The game presents two damage tracks — red numbers for physical harm, blue for lust and mental strain — and the API is full of paired [hp, resolve] tuples. Underneath, they resolve to one variable.

Resolve is HP. Lust is missing HP. calculateDamage folds every component — tease, drug, pheromone and fatigue included — into slot 0 of its return tuple, and slot 1 is returned as a constant zero, so the blue number never renders from the standard attack path. applyDamage still faithfully calls target.resolve(-r) with that zero, which routes back into HP() anyway.

What survives of the distinction is how you lost:

Every hit stamps lastReceivedDamType. At zero HP the engine reads that stamp to decide whether you were beaten or seduced, and routes to a completely different defeat scene. So the two bars are a single resource wearing two coats, and the coat is decided by the last blow.

Falling over

HP() is not a setter; it is a 30-line event. Writing to it can trigger shield bookkeeping, three separate death-saves (the Unbreakable effect, an equipped Senninbari, the InfernalResolve perk), an automatic entry into Frenzy stance below 60% health, an interrupt of any multi-turn attack, and finally onDefeat().

§6 — Combat

The combat loop

CombatManager is a single reusable instance — newCombat() just re-invokes its own constructor to reset ~45 fields. An encounter is configured by assigning callbacks (setVictoryFunc, setDefeatFunc, setFleeFunc, plus condition predicates), pushing combatants in, and calling startCombat().

Turn order interleaves the sides

This is the most interesting piece of combat scheduling in the engine. Each side's combatants are expanded by turnsPerRound() (so a two-action character appears twice), each entry rolls initiative() fresh, and the two lists are sorted independently. Then they are merged with a penalty that grows each time one side takes consecutive turns:

The rest of the round is a straightforward driver. doCombatRound() increments the round, recomputes the order, and walks the list; each turn runs preTurn (effect procs, defeat checks, cooldowns) then mainTurn (multi-turn attack continuation, else combatAI). Because a player-controlled turn has to wait for a click, mainTurn returns a flag and the loop returns out — the button's callback re-enters via continueCombat(). The whole loop is therefore re-entrant rather than blocking.

combatFlow decides who is at the wheel. simTurn() returns true — meaning "let the AI drive" — unless flow is set to full control and the combatant is a non-guest ally. When the player is driving, combatAI is overridden to paint the five equipped powers into buttons instead.

The enemy AI

powerPicker() is a short priority cascade rather than any kind of search:

  1. Below 40% health, use the highest-tier non-basic power available, sorted by power type, then level, then cooldown.
  2. If allies are hurt (≤55%) and a healing power is known: if more than 40% of the party is hurt, pick a heal by weighted roll; otherwise pick one at random.
  3. If nobody is below 90%, drop healing powers from consideration entirely.
  4. Otherwise weight by level + 2 and roll, with special handling for multi-turn powers in a mid-health band.

Aggro is real: applyDamage feeds (hp + resolve)/2 of every hit back into the attacker's threat, and a handful of powers and perks scale threat generation directly. threatTarget() is what most enemies use to choose a victim.

The alias stack

Because the parser reads window.attacker, window.target and window.hitObj, any power that internally invokes another power would clobber those globals mid-sentence. The engine handles this with pushAliases()/popAliases() around doCombatSaveAliases() — an explicit save/restore stack for what are effectively dynamically-scoped variables.

§7 — Powers

Powers are classes that compose

A power is a subclass of Power. The constructor declares metadata; doCombat does the work and returns a result object. That's the entire contract.

That delegation is the norm. Dozens of powers are "NormalAttack with a bonus, plus a rider effect", which keeps weapon handling, dual-wield, crit rules and the whole mitigation chain in exactly one place. There are 522 doCombat overrides in the shipped code.

Four power types drive availability: ATWILL (no cooldown), RECHARGE (numeric cooldown), ENCOUNTER (once per fight — the cooldown is set to a sentinel -2), and ULTIMATE (once per fight, and only one ultimate across the whole loadout, tracked by ultimateUsed).

The 25 power tags do double duty as behaviour switches. meetRequirement() turns them into usability checks: SPELL and CHARM fail while Silenced, WEAPON fails while Disarmed or bare-fisted, MELEE/RANGED/THROWN check the equipped weapon's own tags, DUALWIELD and SHIELD check the loadout. targetSelection() reads ALLY and OMNI to decide which party is targetable. And STEALABLE is what lets the MirrorStance stance permanently learn a power that was just used on you.

Powers can also be multi-turn: setting owner.multiTurnAttack makes the combat loop re-enter the same power object each round, advancing an internal stage, until it completes or is interrupted by damage.

Two behaviours are worth calling out. handleDuplicateAdd() decides what reapplication does: an additive effect sums the durations, everything else takes the max. And extends[] gives effects an inheritance chain independent of the JS class hierarchy — is() instantiates each listed class and recurses, so a query for a generic effect matches all of its specialisations.

A static helper class, CombatEffects, wraps the common applications so content authors never construct effects by hand: addBleeding, addProne, addStunned, addSilenced, addBlinded, twelve add{Type}Resistance variants, and so on — each with sensible default durations.

Effect procs run in preTurn as a flat sweep over [...combatEffects, ...statusEffects, ...perks, ...equipment]. If any proc returns true the combatant loses the turn. There's a special case first: a Banished creature only ticks its damage-over-time effects, then procs the banishment.

§9 — Items

Items, slots and sets

Thirteen equipment slots, declared once in GLOBALS.EQUIP_SLOTS: weaponPrimary, weaponSecondary, head, neck, shoulders, armorSet, topGarment, bottomGarment, waist, hands, feet, ring1, ring2.

The Item base carries a stat block that the derived-stat chain sums over generically:

So evasion() can say v += this.getStatForAllEquipment("evasion") and every item in the game participates without registration. Thirty item tags cover material (METAL, LEATHER, CLOTH), handling (TWOHAND, LIGHT, RANGED, THROWN, SHIELD, CATALYST), exposure (SKIMPY, EXPCHEST, EXPCROTCH, EXPASS, CONCEAL) and economy (UNSELLABLE, UNDROPPABLE, UNIQUE).

Exposure tags feed straight back into the sexual-combat model — isChestVisible(), isAssVisible(), isCrotchVisible() and hasSkimpyAttire() read them, and tease damage and sexiness() read those. Conversely hasHeavyArmor() gates a dozen perks in the other direction. Dressing lightly is a mechanical build choice, not just flavour.

There are 45 equipment sets — a separate registry whose members count how many pieces of themselves are currently worn and grant scaling bonuses. Individual items reach for the set object directly, e.g. spellpower checks new ITEMS.PyromancerSetPiece().numEquippedPieces(this).

Transformation items are a registry of their own: 517 Tf definitions, addressed by 14 TF_* domains (body, limbs, face, head, tail, cock, milk, balls, breasts, butt, pussy, cum, feracity, wings). Each creature carries a reagent counter per domain, and the body's canTf*() predicates gate what a given character will accept — Kitsune, for example, refuse most of them.

§10 — Parser

A bracket language for 88 MB of prose

Every string that reaches the screen passes through Parser.parse(). It implements a small dynamically-scoped templating language whose entire syntax is square brackets and pipes — this is what lets one sentence describe a character whose body, gender, species and clothing are all runtime state.

[pc.hasHair|through your hair|across your head]

pc object — a global, an NPC handle, a quest, or a party hasHair attribute, method, or description token …|… pipe-separated branches

The tokenizer is hand-written rather than a regex, because arguments nest: it scans for an unescaped [, then walks forward counting bracket depth until it balances. Arguments containing whole nested tokens are re-parsed recursively.

Dispatch order

For each token the parser resolves the part before the first dot, in this order:

  1. Runtime overrides. A scene can register temporary tokens via Parser.tempParser("word", fn, …), producing a child parser that shadows the global one for one block of output.
  2. flags. [flags.SOME_FLAG|yes|no] is a boolean branch; with numeric arguments it becomes an exact match, and failing that a range match — [flags.X 0 5 10|none|some|many] picks by which threshold the flag has passed.
  3. Dotted objects. party, eParty, aParty and QUEST_* are special-cased; anything else is looked up on window. If the resolved object is a Creature, the parser remembers it as lastChar.
  4. Bare keywords. dayNight, silly, easy, buttslut, plural/p, singular/s, tps, rand, weightedRand, hitMiss, critHitMiss, atCamp, atFH, atWF, outdoors, shopsOpen, hours, first.

A few of those are unusually neat. [tps|is|are] selects verb agreement using lastChar, so a sentence never has to know whether its subject is the player, a singular NPC, or a plural enemy group. [first|first time text|later text] reads a flag, emits the branch, and sets the flag in one token. And [hitMiss|…|…] reads window.hitObj — which is why powers assign to that global before writing narration.

On a Creature, the attribute is passed through getDescription(), which lowercases the first letter, coerces numeric and boolean arguments, dispatches into simpleParse(), and re-capitalises the result if the token was written capitalised. That one switch handles 341 tokens — every pronoun set (heShe, hisHer, himHer, himselfHerself, plus combat* variants that add colour markup), every kinship term, and every body-part noun and description.

Post-processing

After substitution the parser makes four passes over the finished string:

  • [a] / [An] are replaced by looking ahead to the next word and querying a compiled prefix trie for correct article selection, preserving the token's capitalisation.
  • Escaped \[ and \] are unescaped.
  • Anything in double quotes is wrapped in <i> — dialogue is italicised globally, and %" is the escape hatch for a literal quote.
  • Runs of three or more newlines collapse to two.

Scene text itself is authored as tagged template literals passed through a textify() helper that strips the leading and trailing newline and left-trims every line, so deeply-indented source produces flush prose.

Security note

Parser overrides are serialised into save files as function source and restored with eval(). That is the reason validateAndParseSave() rejects any save containing <, >, or their escaped forms before it will parse the JSON — a blunt guard against script injection through a shared save file.

§11 — Scenes

Fifteen buttons and a stack of scenes

The UI is React, but almost nothing knows that. window.ui is a plain controller holding a state object; render() is debounced and re-renders the React tree from that state. Content code calls free functions:

Buttons live in a fixed 15-slot array — addButton silently ignores any index above 14 — laid out as a 5×3 grid. The navigation compass has permanent addresses in that grid:

mainGameMenu() is the hub every scene returns to, and it drains four queues in a strict order before it will draw a room:

  1. NotifyStack — deferred notifications, each with an optional confirm predicate; grouped by timestamp when shown.
  2. CallbackStack — one-shot continuations. Popped and run, then the function returns.
  3. NoDungeonSceneStack — scenes keyed so they can't double-queue, held back until you're out of a dungeon.
  4. SceneStack — the general queue that content pushes onto when it wants a scene to fire "next time the player is idle".

Only if all four are empty does it print the room description, run the room's runOnEnter hook, paint the standing buttons, and take a checkpoint. All four stacks are UniqueArrays, so pushing the same scene twice is a no-op — that's the deduplication for events that several systems might trigger in the same tick.

Navigation is navTo(room, travelMinutes): record priorLocation, set currentLocation, advance the clock, re-enter mainGameMenu. hookedNavTo is the same thing but consults a per-map travel-hook table first, which is how regions install ambush or random-encounter checks on movement.

§12 — World

Rooms, maps and the clock

A room is a plain object. Regions register batches of them with a key prefix, which is prepended to both the room keys and their exits:

There are 1,019 such definitions across 92 addRooms registrations. Each gets three empty encounter tables attached at registration (combatEncounters, otherEncounters, priorityEncounters) which content then fills.

Room state is not stored per room — it is recomputed. RoomManager.processRooms() runs on every clock tick and every menu return, reads a few dozen quest states and flags into locals, and reassigns descriptions, exits, markers and status across the world. It's a full world-state recalculation rather than an event system, which is slower but means room state can never drift out of sync with quest state.

Four room statuses gate movement — INVIS, NOPATH, DISABLED, NORMAL — and separately flags.NAV_DISABLED is a bitfield (N=1, E=2, S=4, W=8) that a scene can set to pin the player in place for one turn. Discovery has a pity timer:

Two kinds of map

Maps are drawn to a <canvas> with a second overlay canvas for fog. There are two rendering strategies:

  • Dungeon maps have no coordinates. The renderer recursively floods outward from the current room following exit links, placing tiles on a 100-unit grid as it goes. Rooms you haven't reached simply aren't reachable by the walk, so they aren't drawn.
  • Area maps use explicit x/y on each room and draw the region directly.

Fog of war, when enabled, paints an opaque overlay and punches a 140-unit circular hole around each room whose visited flag is set — mainGameMenu sets flags[currentLocation] = 1 on entry purely for this.

The clock

processTime(minutes, jitter, sleeping, checkAchievements) is the world's heartbeat. It recomputes rooms and camps, redraws the map, recomputes the player's race, then — gated on the tutorial being finished — advances timestamp and computes how many hour and day boundaries were crossed. Those two counts are passed down to every subscriber:

Passing boundary counts rather than raw minutes is what lets a twelve-hour Wait fire twelve hourly checks and one daily check without any subscriber having to track its own last-run timestamp. Each Creature.processTime then runs its own cum, hole, milk and pregnancy bookkeeping.

§13 — Trackers

Quests, races and the long tail

Quests are append-only state machines

A quest holds states[] (a description per state index), completedStates[] and failedStates[] (terminal indices), and currStates[] — the history of states entered. The current state is the last element. Only currStates is persisted; everything else is rebuilt from the class.

Because it's a history rather than a scalar, a quest can ask "did this ever pass through state 4?" without any extra flags — which is how optional branches are tracked. setState() refuses to move a completed quest, records the transition, raises an alert flag, and returns a formatted "Side Quest Updated!" blurb for the caller to print. 93 quest ids are defined.

The player's race is computed from their body

NPCs match their race by name. The player does not — PlayerCharacter.calculatedRace() scores every one of the 38 races against the current body and takes the winner. Race.score() works by constructing a pristine clone of the character, applying the candidate race's set() template to it, and diffing:

ComparisonContribution

Template has it, character lacks it−weight ⁄ 2

Weights encode how diagnostic each trait is: skinType is worth 5, armType/legType/faceType/wingType/milkType 3, hornType/earType/gillType 2, tailType/tongueType/nippleType/cumType 1, and hornLength/earLength only 0.5. Because updateRace() is called on every clock tick, accumulating transformations flips your species the moment the balance tips — and your race in turn feeds your stat affinities.

§14 — Persistence

Saves that store only the difference

This is the cleverest part of the engine. A save never contains an object graph — it contains a registry key plus whatever has changed since construction.

An untouched NPC contributes an empty object. Loading reverses it: construct a fresh instance from the class, then apply the diff. Nested objects follow the same rule — an item serialises to { key, args } where args is just its stack count (plus a colour or transformation type for a couple of item classes); an effect to { key, duration, values }; a race to { key } alone.

Migration

doFixes() and doPostFixes() run roughly 50 version-gated repairs on the raw object before and after deserialization, reaching back to save format 0.3.16. They rewrite renamed registry keys, re-prefix room ids, split a rings array into ring1/ring2, backfill equipment slots that didn't exist when the save was written, relocate the player if a map was reworked, and retroactively unlock codex entries. Because everything is stored by key, a migration is usually just a string rewrite.

§15 — Resilience

Designing for the crash

A text game where a scene is an arbitrary function will eventually throw inside one. The engine treats this as expected and builds two recovery layers.

Checkpoints. Every return to mainGameMenu takes one — a full save object held in memory as a JSON string. It's split in two for cost: the cheap half (flags, location, time, options, quests) is captured immediately, and the expensive half (all character diffs and the party) is deferred behind a 1-second debounce that verifies the clock hasn't moved before committing. Entering a dungeon snapshots the current checkpoint into window.inDungeon, giving a second, coarser restore point that survives the whole dungeon.

The error screen. Uncaught exceptions land in handleCriticalError(), which resets the UI controller, prints the stack, and offers a menu:

  • Reload Checkpoint — gated on a checkpoint existing.
  • Reload Dungeon — gated on being in one.
  • Submit Error — only when error reporting is set to "prompt" and Sentry initialised.
  • Restart Game — window.location.reload().

The recovery buttons wrap their own handlers in try/catch and recurse into the error screen on a second failure, with a distinct "Could Not Restore Checkpoint" message so the player isn't stuck in a loop.

The same instinct shows up in the parser: an unresolvable object or attribute emits <b>ERROR: COULD NOT FIND ATTRIBUTE "x" FOR OBJ "y"</b> inline and keeps going, rather than throwing. A typo in a scene produces one visibly broken sentence instead of a dead game.

Error reporting is opt-in with three modes (off / automatic / prompt), pointed at a self-hosted Sentry instance and tagged with the build's release hash. It defaults to off.

Art selection

Character art is filename-addressed: identifier.artist.variant.png, as in alante_bust.Moira.0.png and alissa_bust.DCL.0.png. imageResolver() collects every file matching an identifier and picks one by:

  1. an explicit per-character preference in Options.systemOptions.imagePrefs, if the player set one;
  2. otherwise a ranked artist order, with a special ordering for a few centaur and marefolk portraits.

A parallel pair of helpers, croppedOrFull() and fullOrCropped(), choose between the crops/ and fulls/ directories depending on context. The shipped art is 1,299 full portraits, 1,272 crops, 454 combat busts, 169 CG scenes, 279 achievement icons and 96 UI vectors.

On Electron the resolver additionally warms every portrait and CG by constructing Image objects at boot, trading startup time for no in-scene pop-in.

§17 — Observations

What the design gets right, and where it strains

The load-bearing ideas

  • Classes as content, keys as data. injectKeys plus per-class serialize means saves are small, migrations are usually string rewrites, and a designer adds an item by writing a class — no schema, no registration step, no migration.
  • Diff-against-pristine saves. Serialising a freshly-constructed instance to compute the delta is a genuinely elegant trick. It costs 467 object constructions per save and buys immunity to content additions: any field a new version introduces simply matches its own default and never appears in old saves.
  • Recompute rather than subscribe. Room state, race, and every derived stat are computed on demand from primary state. Nothing can desync, at the cost of doing a lot of work per tick.
  • Fail soft in prose. The parser printing an inline error instead of throwing is the right call for a game where content volume guarantees typos.
  • Boundary-count time. Passing "hours crossed" and "days crossed" rather than elapsed minutes makes every periodic subscriber trivially correct across long waits.

Where it shows its age

  • The globals are the API. 425 globals and 13,098 scene functions in one namespace. It's genuinely ergonomic for content authors — a writer never imports anything — but nothing is analysable, and the alias push/pop stack in combat exists purely to work around dynamically-scoped globals.
  • The modifier chains. armor() is 34 sequential conditions naming specific perks, items and effects. Adding an item means editing a core stat method, so the coupling runs from the engine outward to content instead of the other way.
  • Vestigial Resolve. The HP/Resolve merge left [hp, resolve] tuples threaded through the whole damage API, a resolve(v, absolute) that returns a hardcoded 50 on one branch, and a reduce in calculateDamage that computes hitsResolve() and discards the result. It's dead weight in the hottest path in the game.
  • Eager "lazy" chunks. Every content chunk is awaited at boot, so the splitting buys build hygiene and a progress bar but no load-time benefit.
  • Cloud saves are host-bound. The endpoint is a relative PHP path, which cannot resolve from an Electron file:// page.

The unsurprising one

For all the fantasy machinery, the shape underneath is a fairly ordinary early-2010s web app: a debounced React render over a mutable state bag, a manager per subsystem, and a templating layer. What's unusual is the scale it's been pushed to — a 1,000-member god object, 88 MB of prose, and 1,019 rooms — with almost no architectural change along the way.
