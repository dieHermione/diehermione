technical notes

How the thing is put together, for whoever works on it next. The running handoff in HANDOFF.md is the authority on what changed recently; this page is the shape of the system rather than its history.

SHAPE

One Express server, server.js, serving static files and a JSON API. No database: state is JSON files on disk. No build step: the browser gets the source as written. Deployed on Railway, which redeploys on every push to main.

There is exactly one admin identity, hermione, and a great deal of the product is "what she can do that you cannot".

LAYOUT

server.jsEverything server-side: routes, auth, storage, game rules that must not be client-refereed. elysium-engine.jsThe tree simulation, kept as a pure CommonJS module so it can be exercised with plain node. public/Anything served without a session: the login page and every shared script. views/Pages that require one. Served with sendFile from a route, so the static middleware cannot hand them out. mockups/Design exploration. Parameterised single files, one design per ?d=N, rendering off file://.

STORAGE

Each concern gets its own file under DATA_DIR (the repo root in development). All of them are gitignored: several hold real writing.

users.jsonAccounts, keyed by lowercased username. Points, angelcoins, stats, notifications, daily stamps. games.jsonChess, keyed by the non-admin player, with a snapshot stack behind rewind. deathroll.jsonDeathroll games. elysium.jsonOne tree per account. parses.jsonDummy Parse runs, stored whole with their event lists. summaries.jsonHanded-in summaries. devotion.json
penance.jsonEditable preset line-sets for the two writing games. decrypt.jsonEditable line pool for the login decrypt animation.

Every loader falls back to a built-in default when its file is missing or unparseable, so a fresh deploy and a corrupted file behave the same way: the site comes up.

AUTH

express-session, in memory. Restarting the server signs everyone out; that is accepted rather than solved.

requireLoginA real account. Used where there has to be somewhere to write the result. requirePlayerAn account or a guest. Used by the single-player games. isAdmin(req)The one identity check. Every admin route repeats it; nothing is trusted from the client. playerId(req)One identity for accounts and guests alike, so games can file state under either.

Registration creates the account in a pending state. Pending accounts cannot sign in and do not appear in listings until approved.

Hiding is not access control. Chess is the worked example: the controls only Hermione has live in views/chess-extra.js, behind a route that 404s for everyone else, so the opponent's copy of the page has no trace of them. That is to avoid spoiling the game. The endpoints themselves still check isAdmin on every call, and that is the part that actually matters.

FRONT-END CONVENTIONS

The old shared shell (site.css plus a pill nav) is being retired. New pages are self-contained: one file, its own palette, no shared stylesheet. Several older pages still use the shell, so expect both.

A self-contained page still has to carry a few things the shell used to provide:

  • [hidden] { display: none !important }, because hidden loses to any explicit display.
  • The palette variables the shared scripts read: --c, --dim, --bright, --accent, --glow, --err. The console and the ambience controls theme themselves off these.
  • class="has-top-nav" on the body plus nav.js, which is all the back chevron needs. It gates on siteMe(), so me.js has to come with it.

THE DAY KEY

Everything daily rolls over at 6am America/New_York. todayKey() is the only correct way to ask what day it is: it shifts by the reset hour before taking the date, so "today" means "since the last reset". Comparing Dates directly will be wrong twice a year and wrong every morning.

TRUST

The single-player games referee themselves and report their results. Snake's food count, the writing games' line counts and Dummy Parse's numbers are all taken on trust. This is deliberate: the audience is small and known, and the alternative is simulating each game server-side.

What is not trusted: anything that moves points or ranks, the chess rules, the wheel's outcome, and everything behind isAdmin.

TRAPS THIS CODEBASE HAS ALREADY SPRUNG

  • SVG elements have no hidden or className IDL property. Assigning either silently does nothing. Put state on a wrapper div, or use setAttribute.
  • A filter on page content becomes the containing block for position: fixed descendants, which throws the console and every modal across the screen. Screen effects use backdrop-filter overlays instead.
  • A CSS animation ending in transform: none wipes a positioning transform. Centre with inset or a wrapper if the element also animates.
  • Anything appended to an element that a render function empties will be removed mid-animation. Hang overlays on a parent that survives the repaint.
  • Vertical text is tall. A collapsed panel's rotated heading grew the dashboard grid enough to trigger its scale-to-fit and visibly shrink the whole page. It is out of flow now.
  • crossorigin="anonymous" on audio makes playback need CORS headers the host may not send.
  • Frame-rate dependent probability. Snake's food rolled its escape once per frame, so doubling the speed changed the odds. Roll on the state change, not on the frame.

RECIPES

Adding a game

  • Put the page in views/ and give it a route with requirePlayer, or requireLogin if it has to remember anything.
  • Add it to the list at the top of views/games.html. That is the only place games are listed; the dashboard just links to the wall.
  • Mark it multi: true if a guest cannot play it, and it will be pasted over for them.
  • Add it to GAMES in console.js so pray launch knows the name.

Adding an editable text pool

Follow decrypt.json: a defaults constant, a loader that falls back to it, an open GET if the login page needs it, an admin-only POST, and one more call to the shared preset editor in the admin panel (public/adminpanel.js, its own /admin page).

TESTING

The sandbox is a scratch DATA_DIR and a second port:

DATA_DIR=<scratch> PORT=57999 SESSION_SECRET=sandbox node server.js

Check for a leftover server before trusting any request. One from an earlier session will hold the port, the new one dies with EADDRINUSE, and curl happily answers from the old data. Check with lsof -nP -iTCP:57999 -sTCP:LISTEN, and kill the PID it prints: pkill on the command line kills the shell wrapper and leaves node holding the socket.

Static files under public/ and views/ serve fresh; only server.js changes need a restart.

KNOWN LIMITS

  • Sessions are in memory, so a restart signs everyone out.
  • Writes are whole-file and unsynchronised. Two simultaneous writes to the same file can lose one. The traffic does not warrant more.
  • The photosensitivity flag is read from localStorage on the login page, because that page runs before anyone is identified. A flagged account is unprotected on its first visit from a new browser.
  • Guests are held in memory, so a restart forgets them and their games.
